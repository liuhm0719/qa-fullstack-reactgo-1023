## Deploying this project (astra-deploy)

This project deploys through the Astra CICD platform. The deployment declaration lives in `astra.jsonc` at the repo root; the platform link anchor lives in `.astra/project.json`.

### Step 0 — check the link anchor

If `.astra/project.json` exists, the repo is already initialized: read it and note its project identifier — every deployment below MUST use that identifier, which is what keeps deploys from any environment landing on the same project. An anchored repo is never re-initialized: when the declaration looks stale or broken, use the platform's re-sync or repair flow, which validates and updates it in place. All deployment paths in this guide read the same `astra.jsonc` at the repo root. If the anchor is missing, initialize first:
- astra CLI available: run `astra init --template <template>` (list templates with `astra template list`).
- No CLI: configure the gateway MCP server (Step 2b) and use its project/environment creation tools.

Either path converges on the same project: for a git repository that already has a project on the platform, initialization claims that project instead of creating a duplicate.

### Step 1 — check for the astra CLI

Run `astra --version` to see whether the astra CLI is available in this environment.

### Step 2a — astra CLI available

Run `astra deploy --env staging`. This reads the repo declaration files; configure your token under `~/.astra/profiles`.

### Step 2b — no CLI: use the gateway MCP server

Configure the gateway MCP server at `http://host.docker.internal:18080/mcp` (the bind token authenticates; get it from the platform Settings page — never write it into this repo). Take the project identifier from `.astra/project.json` and pass it as the project_id of the astra deployment tools. Read the repo's `astra.jsonc`, then pass its content as the spec parameter to those tools.

### Step 2c — no CLI: call the gateway REST API directly

The gateway public base URL is not configured — ask the platform administrator for the deploy endpoint.

### Step 3 — after you deploy

Deployments are asynchronous. The deploy call returns an operation id: poll the operation-status tool until the operation is terminal, then read the deployment status — its outputs carry the access URLs (a per-component map plus a single access_url) to hand to the user. On failure, walk the operation's events with the operation-logs tool (cursor-based; phase events name child operations you can drill into). Common failure shapes:
- The build fails: check the git credentials and registry access the platform builds with.
- The deployment never turns healthy: check the component serves GET on its declared health path and listens on the Dockerfile EXPOSE port. A frontend served under a path prefix must expose an explicit health route — its root path redirects, and probes do not follow redirects.
- Never edit `astra.jsonc` or `.astra/project.json` to work around a failure: they are platform-owned. Use the platform's repair flow.

### Red lines (do not cross)

- Tokens and credentials never go into this repo or astra.jsonc.
- astra.jsonc `environments.vars` holds non-sensitive config only; sensitive values go through the platform-side config channel.
